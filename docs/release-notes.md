# 正式发布正文

正式模板的中央来源是 `templates/repository/.github/release-template.md.mustache`。Copier 将其递送到产品 `.github/release-template.md.mustache`。显式声明原生发布工作流的产品也可以使用该工作流锁定的中央模板。构建预检核对产品 S 与执行器提交对应的模板字节。产品 `.release-notes/<unitId>.md` 是候选审阅文稿，由同一候选的生成和编辑保护流程维护。

新模板由发布平台提供发行名称和版本。正文须至少包含一项本版实质内容，由系统附上与固定源码绑定的版本记录。必须执行的操作居首，概述与本版重点择一。其后按适用性展示本次更新、兼容性与迁移、获取与使用、已知问题与限制、贡献者和版本记录。单项修复可直接写入错误修复。只影响兼容性时可直接填写兼容性与迁移。使用本版交付物和读者所需的实际入口填写获取与使用。

候选文件使用二级标题 `必须执行的操作`、`概述`、`本版重点`、各更新分类、`兼容性与迁移`、`获取与使用` 或 `已知问题与限制`。概述为单行段落，其他栏目中的每项以 `**短标题**。具体说明` 开头，条目用空行分隔。说明可以包含公开 HTTPS 链接，获取与使用的条目可以另附多行 fenced 示例。预览与冻结正文用同一 Mustache 投影这些栏目。贡献者与版本记录由执行器加入。

文档本身属于交付，或实质修订会影响本版读者判断或操作时，才填写文档更新。生成器通过版本区间中的文档原文或文本差异取证，并由候选审阅确认使用者影响。普通 README 维护、文件位置、标签和提交标题可用于定位变化。安装、升级与引用要求应写在读者对应的操作栏目，并链接细节。

新模板适用于纳入 SPLRAD 治理的组织仓。Steward 从上一版边界至本版受审源码取实际变更的 GitHub commit author，按数值 ID 与已确认的真人账号取交集并去重。符合条件的贡献者以可点击的 48 px GitHub 头像展示，包含实际贡献的组织成员。机器人、服务账号及 GitHub `web-flow` 的原生 ID `19864447` 也要排除。名单为空时省略整节。

已有正面确认的项目可在默认分支通过受审提交提供可选的 `.github/release-contributors.json`，格式为 `[{"id":123,"evidence":"仓库负责人直接确认该数值 ID 对应真人的可核验记录引用"}]`。确认记录只需引用依据，GitHub 数值 ID 用于与本版提交身份核对。在候选基础提交读取确认信息，人工候选校验使用默认分支源码，冻结时按受审合并提交复核。

使用旧模板锁定的候选、人工稿和历史周期沿用其原有配置和格式。人工编辑保护和候选内容恢复继续核对对应源码、原始输入和文稿。

签名封存入口使用受审源码重新渲染新模板，逐字节比较待封存文件。发行版本和 tag 由 manifest 绑定。产品工作流选择 GitHub 子集时，旧模板按原规则投影下载区。新模板在保持封存正文原字节的同时，核验其中的直链全部指向工作流实际选择的附件。

采用交付合同 v3 的产品在原生工作流锁定的受审源码和原制品上生成正文。原生投递回执继续绑定工作流、Run、attempt、制品 ID 和摘要。恢复使用同一回执和同一份受审正文来源。

修订已有签名附件的公开正文时，产品在受保护的默认分支采用 `.release-notes/published/<releaseId>.md`，文件首行使用 `<!-- release-body [仓库数字ID,发行数字ID,"tag","源码SHA","原附件SHA256"] -->`，紧接换行及完整新版 Markdown。验证器在固定默认分支提交读取该路径，验证最近修改该文件的提交签名、文件字节和对应发行身份。网页仅采用首行之后的正文，附件、签名和历史生产回执继续按原件验证。
