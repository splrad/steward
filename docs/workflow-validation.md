# 工作流校验合同

## 普通工作流变更

可信中央 runner 校验工作流安全边界。Steward 的 config/repositories.json 中 allowedWorkflowPaths 描述候选仓库的实际清单：同一个 PR 可以同步增加、删除或改名普通工作流及清单，不需要先向默认分支登记文件名。清单与实际文件必须完全一致。

候选清单不能定义安全规则。必需 pr-validation.yml 由可信策略要求存在；其 validate 作业、策略来源 SHA、固定中央检出、验证命令及 PR 事件覆盖由可信 runner 的入口合同保护。显示名称可变，跳过条件、吞错、额外执行步骤和候选策略替换会被拒绝。修改这个必需安全入口仍属于中央策略变更。

普通工作流统一检查：显式只读/none GITHUB_TOKEN 权限、允许的事件类型、受信且锁定提交的 Action、禁用 checkout 凭据持久化、普通文件/YAML 唯一键、禁止可复用作业和本地 Action 绕过、禁止 PR 作业获取受保护环境或密钥。密钥引用必须是显式名称，并匹配中央规定的环境。发布说明模型与 App 密钥使用不同环境。自托管 runner 拒绝；现有动态构建 runner 只允许来自受保护 release plan 的隔离无密钥作业，具体输出合法性由构建合同继续验证。

现有 actionlint、业务工作流合同、类型、测试、配置和 dist 检查全部保留。scripts/verify-workflows.mjs 复用同一通用模块，移除重复的文件名数组；其中业务作业的专门合同仍须随业务变更同步更新。新增 Action 供应商、权限、密钥或环境属于安全能力变化，需要中央策略审查，不由候选清单放行。

静态校验不证明任意 shell 命令安全，也不等于线上环境已具备审批。代码审查、平台环境保护和人工发布授权继续承担各自责任。

## 部署隔离的合并前置条件

检查时 steward-deployment 仅允许 main 分支，没有 required reviewers。main 上 runner/config 变更会触发部署，前置 PR 合入也不例外。

合并前由另行获授权的管理员保留 main 限制，并增加独立 required reviewers、禁止自审批及管理员绕过。核对全部远程迁移和部署步骤都受该环境保护。若账户能力或维护者配置不能满足要求，保持不合并，另行制定代码级部署隔离方案。批准代码合并不等于批准等待中的部署。

本 PR 不修改线上规则、部署工作流、运行时或数据库。可信验证策略经默认分支工作流使用，无需先部署 Worker。

## 验收依据

正向覆盖普通工作流新增、改名、删除、清单同步及必需入口显示名称变化。反向覆盖清单自授权、必需入口移除/替换/跳过/吞错、额外执行步骤、事件过滤、隐式/写权限、不固定 Action、本地 Action、凭据持久化、密钥混用、表达式密钥索引、PR环境、非许可 runner、重复 YAML 键及别名。

端到端用例确认可信检查通过后仍执行下游任务，失败不会转换成成功。实际 #253 工作树的通用安全校验通过，仅证明该层兼容，不替代其未来合并候选上的完整 CI 和审查。
