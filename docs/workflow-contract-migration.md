# 工作流合同与可信入口迁移

## 当前实现边界

本版本将合同解析、独立批准、可信入口校验和门禁复核接在同一条验证路径上。线上启用配置 `config/workflow-contract-authority.json` 保持空仓库表；没有新增批准者，也没有启用任何仓库。

版本 1 支持：

- 普通工作流按既有安全内核检查。
- 在批准后退役业务 fragments 作业，保留可信 validate 入口。
- 按仓库和资源名声明跨工作流共享队列，禁止取消运行。
- 基于受保护 base 上已采用的合同进行差异判断。已采用的合同不要求后续每个业务 PR 重复批准。
- 使用原生审查的独立人工 APPROVED 记录批准合同差异，绑定仓库、PR、head、base、策略 SHA 和合同摘要。
- 在可信运行结束、审查事件、PR 更新和定时回读时重新检查批准。撤销、正文改变、权限丢失、版本漂移和 API 失败均不能生成成功。

版本 1 通过固定能力协议支持可信策略来源解析及隔离产物验收。#253 的实际同步、构建和完成回调工作流已接入这些能力。静态校验、执行器测试和本地双平台验证覆盖这些改动；线上工作流、环境保护和规则切换仍需单独授权后验证。

可信策略解析器从工作流自身的不可变提交启动，使用编译进执行器的来源登记。它读取固定 HTTPS 健康端点，拒绝重定向，限制响应大小；随后核对仓库身份、默认分支历史及部署运行的仓库、路径、事件、结论和提交，再次读取健康端点防止策略漂移。矩阵消费者还要求解析结果与前置作业一致。候选声明不能提供健康地址或替换解析命令。受保护作业只在解析后检出精确策略，后续命令固定在独立的 policy-live 目录运行。

构建回调按 resolve → inspect → accept 交接。inspect 作业没有 App 凭据，在独立 runner 中检查原生版本。accept 重新读取成功运行、当前 attempt、唯一产物及 GitHub 摘要，重新下载并复算原始 ZIP 和每个文件的字节摘要，与隔离报告和持久化构建计划逐项比较；只写入验证后的资产和 seed，然后请求运行时接受。此阶段不调用原生检查器或执行产品代码。确定的检查失败进入 reject；网络等基础设施失败保留重试路径。

文件交接采用流式落盘及逐文件核验，保持发布合同原有的最多 128 个扁平文件、单文件 1 GiB、展开总量 4 GiB 预算；ZIP 下载预算额外保留 16 MiB 封装开销，支持 ZIP64，报告最多 60000 个 base64 字符。拒绝路径、重名（含大小写碰撞）、设备名、链接、加密、CRC 错误及超限内容。目录型发布资产和 OCI 发布不属于既有文件收据合同，继续拒绝。

## 数据与授权来源

候选声明位于 `.github/workflow-contract.json`：

```json
{
  "version": 1,
  "repositoryId": 1296724484,
  "fragments": "retired",
  "sharedQueues": {
    ".github/workflows/release-build.yml": "release-build"
  }
}
```

共享队列必须为 `workflow-resource:<repositoryId>:<resource>`，并显式关闭 cancellation。缺失、未知字段、动态资源名、跨仓库标识和不存在的工作流或作业都被拒绝。作业级声明使用 `.github/workflows/name.yml:job`。本次正文写入者共同使用 `pr-body` 资源，保守串行处理全部受管仓库；其他操作仍使用各工作流隔离的并发组。

验证器来源由独立的 `WORKFLOW_EVALUATOR_SHA` 固定；它与发布、构建和运行时部署使用的严格 `POLICY_SHA` 分开。普通部署保留该验证器指针，无需重新签发工作流合同批准。运行时按该不可变 SHA 从中央仓库读取授权配置，读取失败即阻断，不采用当前部署或候选目录中的替代配置。发布候选验收分别核对 Classification 的发布策略版本和 Validation 的可信验证器版本。

批准者 ID 和初始合同来自可信验证器版本中的 `config/workflow-contract-authority.json`。候选目录中的同名文件不参与授权判断。批准者必须是配置中的人类账号、当前具备写入及以上权限，且不是 PR 作者。空批准者列表不能启用仓库。本文不指定实际批准者。

系统生成审批文本；审批人对当前提交提交原生 APPROVED Review，正文为该文本。批准只影响合同选择，不等于合并、部署或发布授权。正文含完整版本绑定，普通“同意”、标签、机器人评论和 AI 审查结论不产生授权。

读取候选合同和基线合同均固定到相应提交。读取审查后再次读取 PR，防止取证期间发生推送。缺失合同恢复初始合同要求；403 或网络错误不能降级成缺失。

可信 runner 在候选任务运行前消费并移除合同只读令牌。执行器来源仍由固定校验入口控制。运行时仅处理受信 required-workflow 的实际运行，并核对机器证据步骤中的策略版本；不能把一个用户自建同名检查当作证据。

## 首次启用：固定审查版本后交接

已只读核实的线上事实（2026-10-20）：

- 组织 `Default Branch Protection` 规则集 18883080 为 active，没有 bypass actor。
- required workflow 为 Steward 仓库中的 `.github/workflows/pr-validation.yml`，当前跟随 `refs/heads/main`。
- 当前必需 status check 包含 App 4243096 的 `PR Classification Gate`；`PR Validation Gate` 尚未列为必需项。
- `steward-deployment` 环境只有分支策略，没有人工审批，并允许管理员绕过。不能把“先不部署”的文字当作部署隔离。

GitHub 官方组织 ruleset API 支持 workflow 的 `sha` 字段：
https://docs.github.com/en/rest/orgs/rules

因此首次启用不依赖先合一个前置业务 PR。它依赖管理员对一个已经冻结并独立审查的执行器版本进行一次显式信任交接：

1. **冻结和审查执行器。** 先为所有将切换到 v2 入口的受管仓库配置实际的独立批准者和初始合同，逐项核对受保护 base 上已有合同是否经过采纳；不能把此前预置但未审查的声明自动当作已批准。当前授权表为空，禁止直接启用此构建。v2 发布基线要求显式退役 fragments；仍需要旧片段执行器的仓库继续保留旧入口，直到该仓库的迁移获得批准。若规则集覆盖多个仓库，必须先核对全部受影响仓库都满足上述条件；有任一仓库仍依赖旧入口时，整体切换停止，不能以空授权表或静默跳过片段校验继续。完成所有能力和双平台测试后，经用户授权才创建签署提交并推送。记录不可变提交 SHA、runner 产物摘要、测试日志及独立审查记录。执行器必须使用可信配置，不得把自身候选配置当授权。尚未审查的提交不能进入下一步。
2. **建立部署隔离。** 经单独授权，在部署环境启用独立审批、禁止自审批和管理员绕过，验证待部署运行确实停在审批处；精确限制迁移版本的部署来源。保存原设置并准备恢复。隔离未验证时停止，不能让主分支更新自动部署。
3. **独立启用对应运行时版本。** 冻结提交完成后，经管理员授权将仓库变量 `WORKFLOW_EVALUATOR_SHA` 设为已审查的完整 SHA；该值在提交外设置，避免把提交自身 SHA 写入源码造成循环。部署前身份校验必须先于数据库迁移，缺失或格式错误即停止。审批并部署支持该执行器协议的运行时，回读健康端点 `policySha`（部署版本）、`evaluatorSha`（固定验证器）、部署身份、Webhook 审查事件和定时复核能力。该操作只在得到部署授权后执行；不能依赖先合并新代码才获得验证能力。若环境不允许该冻结来源，必须先批准并配置精确来源，不能临时开放全部分支。
4. **保持规则 active，替换可信入口来源。** 管理员将既有 required workflow 从跟随 main 改为冻结执行器的 SHA（先核对 GitHub 接受该不可变来源；API 的 sha 字段不是已完成线上演练的证明），同时将 `PR Validation Gate` 绑定 App 4243096 加为必需检查。保留原审批数、审查线程要求、Classification Gate、防删除、防强推和其他规则。不得添加 bypass、关闭规则或删除旧检查来制造通过。
5. **独立回读。** 核对规则完整差异和 source SHA；让新的 required workflow 真正运行。用合法变更、无批准合同、旧 head 批准、撤销批准和伪造来源分别验证实际阻断。历史成功运行不能代替新运行。
6. **业务 PR 正常通过新门禁。** 合同改变在同一 PR 获得独立批准，实现仍须通过安全内核和全部验证。达到要求后由用户另行决定合并。合并本身不授权环境审批或部署。
7. **保持固定版本治理。** 可长期固定已审查的执行器 SHA；仓库变量、运行时健康读数和 required workflow 来源三者须一致。以后普通业务合同随 PR 采用，不需要改该指针；新增执行器能力才进行一次新的版本审查和指针交接。

`planWorkflowGateMigration` 只生成 before/after 提案，不调用 GitHub 写接口。测试验证它保留既有规则、拒绝弱化来源，并且重复生成不会增加重复检查。

失败恢复：

- 新入口未确认时阻止合并，保留全部审批和保护要求。
- 需要回退时，恢复已保存的可信旧来源和匹配运行时，再回读；旧规则可能继续拒绝新合同，这是安全阻断，不允许伪装通过。
- 没有发生合并时不需要业务数据回滚；部署回退必须核对实际版本和数据迁移兼容性。
- 当前没有自动回滚脚本或线上执行授权。任何线上交接都需要明确授权。

这种交接以外部管理员批准的不可变执行器作为信任根，打断“新代码必须先通过只认识旧代码的门禁才能成为门禁”的循环。它不要求关闭旧保护，但确实需要一次受控的规则来源切换和运行时部署。

## 首次启用的停止条件与回退清单

2026-10-20 再次只读回读：规则集 18883080 仍为 active、无 bypass、覆盖全部仓库，required workflow 跟随 main；部署环境仍无人工审批且允许管理员绕过。授权表仍为空。上述步骤是迁移目标，当前尚不具备执行条件。

特别需要在演练前解决运行时引导问题：直接从未合并分支部署本 PR 会把 POLICY_SHA 改为该分支提交。可信来源解析要求成功的默认分支 push 部署及默认分支历史；该部署不能满足此条件。共享同步及使用严格策略绑定的旧候选会失败关闭，分类调度也须核对默认分支执行版本。不能把“允许迁移分支部署”当作已打断所有循环依赖的证据。第 3 步在证明旧分类/发布服务持续有效、且新验证器可独立服务之前禁止执行；本版本未实现或验证这种引导隔离。

启用前必须形成以下可审阅清单：

1. 当前规则集完整快照、所有覆盖仓库及其初始合同、独立批准者 ID、未完成 PR 和发布候选列表。未配置的仓库不得切换；不能默认接受候选声明。
2. 已冻结执行器 SHA、runner 摘要、双平台验证、两方复审，以及独立人工批准。当前空表版本不能充当启用版本。
3. 旧运行时版本与 POLICY_SHA、验证器变量、部署环境和数据库迁移清单及备份。0015 等新增迁移需逐项证明旧程序仍可读写，不能仅凭数据库迁移成功判断可回退。
4. 在隔离环境演练引导交接：保持旧分类与发布策略服务可用；新验证器读取固定来源；合同批准/撤销立即重算；再演练入口切换和回退。未合并来源、错误 SHA、空表、缺失仓库、撤销批准均须失败关闭。没有演练证据不得安排线上切换。
5. 经另行授权后，按部署隔离 → 已验证的引导交接 → active 规则原子更新 → 正反向实际运行与回读执行。仅在最终状态验证后开放正常合并；审批、部署、规则修改分别留证。

影响范围包括组织内所有受覆盖仓库、在途 PR 的验证重跑，以及运行时版本变化对旧收据和候选的严格策略绑定。共享正文队列会增加串行等待。新策略不能继承旧候选的批准；已开始发布的候选禁止策略迁移。迁移窗口内应冻结新的发布启动并先盘点在途执行，不能假设修改 CI 与发布无关。

回退按实际到达的阶段执行：尚未切换入口时撤销未采用的启用配置并保留旧服务；入口已切换时停止合并和发布启动，恢复保存的可信来源与匹配服务，再核对原审批、App 所有者和所有必需检查，确认没有新增 bypass 或删除原有保护。恢复旧入口后 #253 可能再次被阻断，这是预期的安全结果。部署环境的新增保护不自动撤销。数据库优先保留追加结构和历史记录，仅在证明旧程序兼容后切回旧程序；不自动执行反向 D1 迁移、删除新收据或覆盖备份。

## 消除引导循环的修订方案（待采用与实现）

可执行的交接需要把首次验证器启用与整套发布运行时升级拆开。建议在迁移期使用独立的、仅负责工作流合同验证的运行实例，旧生产运行时继续负责 Classification、发布与同步，POLICY_SHA 保持不变。该方案新增临时运行实例及凭据配置，尚未实现，也没有部署授权。

迁移实例使用已独立审查的固定执行器和授权表，只读取 required-workflow 运行/步骤、PR 和原生审查，写入独立检查名 Workflow Contract Gate；不提供发布、构建、正文写入、迁移数据库或派发业务工作流的接口。凭据限制为所需仓库的 metadata/contents/actions/pull_requests 读取及 checks 写入。新检查名避免旧运行时覆盖它；固定其实际 App 所有者，不接受同名用户检查。运行与审查撤销须有持续复核，缺失或失败不产生成功。

经单独授权并完成隔离演练后：先部署该实例并验证其只读业务边界，再保持组织规则 active，将 required workflow 固定到审查 SHA，同时追加该 App 所有的 Workflow Contract Gate，保留原 Classification 和所有其他保护。由固定入口运行 #253，独立人工批准精确合同，再核对新旧必需检查和全部原线程。只有用户另行批准后才允许合并。

业务 PR 合并后，仍须另行批准部署生产运行时。从真正的默认分支部署新版本，核验 POLICY_SHA、默认分支成功部署、数据库兼容性及正式 PR Validation Gate。先让正式 Gate 成为必需并通过真实正反例，再原子移除临时 Gate 要求，最后停用临时实例及撤销其凭据。交接期间始终至少有一个持续复核的新合同 Gate 为必需；不能先删除临时检查再等待正式检查。

此方案无需先合另一个前置 PR，但有一次临时实例的配置、运行和退役成本。临时方案失败时，保持旧生产服务，恢复保存的旧 required-workflow 来源并撤销未采用的新检查要求；原有检查和审批不能删除。#253 重新阻断，不涉及生产数据库回退。生产运行时升级后的回退则按前述数据库兼容性清单执行。未获该新增组件的明确采用授权前，不创建实例、App、凭据或线上规则。

## #253 验证口径

历史夹具保存 #253 提交 ab3cddd7727917284084899397f161c3d31a0161 的 11 个工作流，验证原来的动态 runner、未授权 fragments 退役和受保护下载确实被拒绝。

实际工作树中的 11 个工作流全部经过同一安全内核检查，使用显式的已批准合同测试输入。生产入口仍会读取 GitHub 独立批准，不能凭本地文件自授权。

- release-build.yml 和 product-build.yml 已拆成 Windows/Linux 静态作业。两者按计划输出互斥，未知或缺失输出使计划失败。
- 两个同步工作流采用可信解析协议；工作流改名不影响协议，修改来源、命令、目录或加入额外步骤会失败。
- 完成回调分离解析、隔离检查、受保护验收和确定失败回写。覆盖真实文件字节检查、版本不符、报告篡改、错误 run/attempt/策略、同名多产物、下载地址、摘要、部分 seed、接受后交付重试和凭据续期。
- 保留原生格式检查、构建预算、严格 POLICY_SHA、已接受构建身份、候选变更重新审阅及过期生成凭证提示 Re-run all jobs 的约束。
- 其他仓库和不同工作流名称的用例验证同一协议不依赖 PR 编号或整份业务工作流摘要。

## 验收与线上边界

本地完整 verify 包含测试、类型、配置、产物重建一致性、安全内核、业务工作流合同和 actionlint。Windows 与 Linux 使用同一最终源码和产物，分别执行完整验证。结果记录在本次工作证据中。

代码提交和本地验证不代表运行时启用。本地验证不能证明 GitHub 已运行这些工作流，也不能证明部署隔离已生效。首次启用必须按上述步骤逐项取得真实回读，任何一步不满足均保持阻断。
