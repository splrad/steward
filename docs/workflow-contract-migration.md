# 工作流合同与可信入口迁移

## 当前实现边界

本版本将合同解析、独立批准、可信入口校验和门禁复核接在同一条验证路径上。线上启用配置 `config/workflow-contract-authority.json` 保持空仓库表；没有新增批准者，也没有启用任何仓库。

版本 1 支持：

- 普通工作流按既有安全内核检查。
- 在批准后退役业务 fragments 作业，保留可信 validate 入口。
- 按仓库和资源名声明跨工作流共享队列，禁止取消运行。
- 基于受保护 base 上已采用的合同进行差异判断。已采用的合同不要求后续每个业务 PR 重复批准。
- 使用原生审查的独立人工 APPROVED 记录批准合同差异，绑定仓库、PR、head、base、策略 SHA 和合同摘要。
- 在可信运行结束、审查事件、PR 更新和定时回读时重新检查批准。撤销、正文改变、权限丢失、版本漂移和 API 失败均不能生成成功。

版本 1 通过固定能力协议支持可信策略来源解析及隔离产物验收。#253 的实际同步、构建和完成回调工作流已接入这些能力。静态校验、执行器测试和本地双平台验证覆盖这些改动；线上工作流、环境保护和规则切换仍需单独授权后验证。

可信策略解析器从工作流自身的不可变提交启动，使用编译进执行器的来源登记。它读取固定 HTTPS 健康端点，拒绝重定向，限制响应大小；随后核对仓库身份、默认分支历史及部署运行的仓库、路径、事件、结论和提交，再次读取健康端点防止策略漂移。矩阵消费者还要求解析结果与前置作业一致。候选声明不能提供健康地址或替换解析命令。可信后缀只接受已定义的同步命令协议及完整环境键集合，禁止附加命令、NODE_OPTIONS、额外秘密或额外步骤。受保护作业只在解析后检出精确策略，后续命令固定在独立的 policy-live 目录运行。

构建回调按 resolve → inspect → accept 交接。inspect 作业没有 App 凭据，在独立 runner 中检查原生版本。accept 重新读取成功运行、当前 attempt、唯一产物及 GitHub 摘要，重新下载并复算原始 ZIP 和每个文件的字节摘要，与隔离报告和持久化构建计划逐项比较；只写入验证后的资产和 seed，然后请求运行时接受。此阶段不调用原生检查器或执行产品代码。确定的检查失败进入 reject；网络等基础设施失败保留重试路径。

文件交接采用流式落盘及逐文件核验，保持发布合同原有的最多 128 个扁平文件、单文件 1 GiB、展开总量 4 GiB 预算；ZIP 下载预算额外保留 16 MiB 封装开销，支持 ZIP64，报告仅传运行绑定、ZIP 摘要和完整规范清单摘要，最多 60000 个 base64 字符；验收端重新构建完整清单并比较摘要，清单不占用作业输出和环境变量通道。下载按已核实归档大小以 4 MiB/s 加 60 秒建立预算。拒绝路径、重名（含大小写碰撞）、设备名、链接、加密、CRC 错误及超限内容。目录型发布资产和 OCI 发布不属于既有文件收据合同，继续拒绝。

## 数据与授权来源

候选声明位于 `.github/workflow-contract.json`：

```json
{
  "version": 1,
  "repositoryId": 1296724484,
  "fragments": "retired",
  "sharedQueues": {
    ".github/workflows/release-build.yml": "release-build"
  }
}
```

共享队列必须为 `workflow-resource:<repositoryId>:<resource>`，并显式关闭 cancellation。缺失、未知字段、动态资源名、跨仓库标识和不存在的工作流或作业都被拒绝。作业级声明使用 `.github/workflows/name.yml:job`。本次正文写入者共同使用 `pr-body` 资源，保守串行处理全部受管仓库；其他操作仍使用各工作流隔离的并发组。

验证器来源由独立的 `WORKFLOW_EVALUATOR_SHA` 固定；它与发布、构建和运行时部署使用的严格 `POLICY_SHA` 分开。普通部署保留该验证器指针，无需重新签发工作流合同批准。运行时按该不可变 SHA 从中央仓库读取授权配置，读取失败即阻断，不采用当前部署或候选目录中的替代配置。发布候选验收分别核对 Classification 的发布策略版本和 Validation 的可信验证器版本。

批准者 ID 和初始合同来自可信验证器版本中的 `config/workflow-contract-authority.json`。候选目录中的同名文件不参与授权判断。批准者必须是配置中的人类账号、当前具备写入及以上权限，且不是 PR 作者。空批准者列表不能启用仓库。本文不指定实际批准者。

系统生成审批文本；审批人对当前提交提交原生 APPROVED Review，正文为该文本。批准只影响合同选择，不等于合并、部署或发布授权。正文含完整版本绑定，普通“同意”、标签、机器人评论和 AI 审查结论不产生授权。

读取候选合同和基线合同均固定到相应提交。读取审查后再次读取 PR，防止取证期间发生推送。缺失合同恢复初始合同要求；403 或网络错误不能降级成缺失。

可信 runner 在候选任务运行前消费并移除合同只读令牌。执行器来源仍由固定校验入口控制。运行时仅处理受信 required-workflow 的实际运行，并核对机器证据步骤中的策略版本；不能把一个用户自建同名检查当作证据。

## 通用工作流演进与首次启用

本方案承接总基线 v1.8、平台 v3.17 及 2026-10-20 采用的 WORKFLOW-EVOLUTION 条款。

1. 已支持的普通工作流修改在同一 PR 更新 YAML、配置、消费方、测试和 runner 产物。必需入口单独保护，普通工作流按安全内核检查；文件数量、整目录白名单或整份业务 YAML 摘要不作为演进许可。
2. 已支持的声明式合同变更在同一 PR 提交声明，由受信配置中的独立人类批准者对精确 repo、PR、head、base、验证器和合同摘要提交原生 APPROVED Review。权限撤销、批准撤销或绑定变化均重新判断。合同批准不授权合并或部署。
3. 新验证能力或信任边界变化需要独立审查升级。仅当现有验证器无法安全验证自身升级时，才需要首次能力交接；以后的普通工作流修改不重复这一前置步骤。

Profile 由固定执行器目录中的 catalog 选择，未知公开仓库使用公开默认配置，未知私有仓库失败关闭。候选仓库不得替换该目录。声明只选择受支持的行为，不能修改安全内核、批准者或可信来源。

### 已核实的阻断链

2026-10-20 的只读证据：required workflow 跟随 main；#256 已合入，拆开了必需入口与普通工作流检查。当前 main 的验证器仍要求普通并发使用隔离 workflow-ref 命名空间，因此拒绝 #253 的共享队列。#253 的通用合同实现已有对应能力，但授权表 repositories 为空，不能直接启用。

组织规则集 18883080 为 active，无 bypass，覆盖全部仓库。必需 status check 为 App 4243096 的 PR Classification Gate；PR Validation Gate 尚未加入。部署环境 steward-deployment 只有分支策略，没有人工审批，允许管理员绕过。以上是调查时状态，执行交接前必须重新读取。

直接部署未合并的 #253 会让 POLICY_SHA 指向分支提交，无法满足默认分支 push 部署及默认分支历史的可信来源合同。首次能力升级必须是现有运行时的正式版本升级，并走正常审查、合入与部署程序。WORKFLOW_EVALUATOR_SHA 只固定验证器，不能替代业务与部署的严格 POLICY_SHA。

### 首次交接顺序与验收

1. 为现有正式运行时准备最小通用验证能力升级，验证它能通过当前可信入口；若不能，记录具体不支持的能力及独立审查所需交接，不删除检查或以候选配置自授权。该工作包必须与业务发布链路和已采用总基线一致。
2. 独立核对规则覆盖的全部仓库、受保护 base 合同的采纳证据、实际批准者及其权限。空表、缺失仓库和未审查的预置合同均不能启用。管理员须核对完整组织清单；只读令牌看不到的私有仓库不能因 API 未返回而视为不存在。
3. 冻结升级提交，记录 runner 摘要、Windows/Linux 验证及独立审查。在数据库迁移前，部署预检从固定 evaluator SHA 读取授权表，检查可信 catalog 和可读取组织仓库的覆盖，以及支持的合同能力。此预检是必要条件，不代替管理员完整范围审计、实际权限核验或批准。
4. 另行授权后建立并验证部署隔离，通过一次正常合入与部署启用正式版本，回读 POLICY_SHA、WORKFLOW_EVALUATOR_SHA、默认分支部署来源、健康状态、Webhook 与定时复核。升级前盘点在途候选并核对数据库兼容性，旧候选不能自动继承新版本批准。
5. 另行授权后，在保持规则 active、原审批和保护要求的前提下固定 required workflow 的不可变来源，并将 App 所有的 PR Validation Gate 纳入必需检查。GitHub API 支持 workflow sha 字段，但字段存在不等于交接成功，须读取实际规则和运行来源。
6. 验证合法同 PR 变更、无批准合同、旧 head 批准、权限撤销、批准撤销、错误执行器和伪造检查。所有覆盖仓库均需具备实际验收证据，然后让 #253 按新合同接受独立审查。

首次能力交接完成后，普通工作流增删、改名、拆分，以及既有能力范围内的声明变更可在同一业务 PR 完成。后续只有新增验证能力或信任边界变化才重复版本审查和受控交接。沿用同一 Worker、App、部署工作流和 PR Validation Gate。

当前任务只修改和验证代码、推送及处理有证据支持的评论；合并、部署、配置批准者和线上规则变更尚未执行。旧验证器继续阻断新合同属于未完成启用的真实状态，不能以本地绿色测试标为已解决。

失败时保持阻断，保存实际到达阶段及来源快照；恢复必须使用匹配的正式版本并验证数据库兼容性，不自动删除数据或反向迁移。规则来源和服务恢复需要对应授权。

## #253 验证口径

历史夹具保存 #253 提交 ab3cddd7727917284084899397f161c3d31a0161 的 11 个工作流，验证原来的动态 runner、未授权 fragments 退役和受保护下载确实被拒绝。

实际工作树中的所有工作流均经过同一安全内核检查，使用显式的已批准合同测试输入。生产入口仍会读取 GitHub 独立批准，不能凭本地文件自授权。

- release-build.yml 和 product-build.yml 已拆成 Windows/Linux 静态作业。两者按计划输出互斥，未知或缺失输出使计划失败。
- 两个同步工作流采用可信解析协议；工作流改名不影响协议，修改来源、命令、目录或加入额外步骤会失败。
- 完成回调分离解析、隔离检查、受保护验收和确定失败回写。覆盖真实文件字节检查、版本不符、报告篡改、错误 run/attempt/策略、同名多产物、下载地址、摘要、部分 seed、接受后交付重试和凭据续期。
- 保留原生格式检查、构建预算、严格 POLICY_SHA、已接受构建身份、候选变更重新审阅及过期生成凭证提示 Re-run all jobs 的约束。
- 其他仓库和不同工作流名称的用例验证同一协议不依赖 PR 编号或整份业务工作流摘要。

## 验收与线上边界

本地完整 verify 包含测试、类型、配置、产物重建一致性、安全内核、业务工作流合同和 actionlint。Windows 与 Linux 使用同一最终源码和产物，分别执行完整验证。结果记录在本次工作证据中。

代码提交和本地验证不代表运行时启用。本地验证不能证明 GitHub 已运行这些工作流，也不能证明部署隔离已生效。首次启用必须按上述步骤逐项取得真实回读，任何一步不满足均保持阻断。

发布作业使用 queue: max，最多容纳100个等待项，并保持 cancel-in-progress: false。顺序按进入并发队列的时间确定，不承诺按版本号或派发时间排序；队列满仍可能取消新增项。参见 GitHub 官方 workflow syntax 的 concurrency.queue 说明。

### 发布链路超时预算

隔离验收 `inspect` 使用 360 分钟作业上限，与构建及受保护验收作业一致。预算测试直接读取实际工作流和运行时常量，避免单独修改子步骤后遗漏外层上限。

| 阶段 | 最大合同内预算与余量 | 作业上限 |
| --- | --- | --- |
| 来源计划 | 45 分钟整体步骤 + 15 分钟初始化余量 | 60 分钟 |
| Windows/Linux 构建 | 45 分钟构建 + 128 × 2 分钟原生检查 + 约 18.14 分钟传输 + 30 分钟准备、文件处理及收尾余量，约 349.14 分钟 | 360 分钟 |
| 隔离验收 | 约 18.14 分钟下载 + 256 分钟原生检查 + 30 分钟解压、哈希及初始化余量，约 304.14 分钟 | 360 分钟 |
| 受保护验收 | 重新下载、核对清单及交接；不重复原生检查 | 360 分钟 |
| prepare / generated-candidate | 约 18.14 分钟资产传输 + 30 分钟文件处理及初始化余量 | 60 分钟 |
| generation-ticket / generation-continue | 读取已核实seed和32 MiB以内来源，分批准备节点或调度下一段，不下载构建资产 | 60 分钟 |
| generate | 每段最多60次、每次3分钟；段内210分钟，来源传输和初始化在额外30分钟内 | 240 分钟 |
| publish | 根据资产大小和数量累计下载、逐文件上传与回读；128 个文件合计 4 GiB 时为 328 分钟 | 动态计算，合同上限内不超过 360 分钟 |

传输预算按 4 MiB/s 计算；余量是预算假设，不是对网络、磁盘或 hosted runner 实际耗时的保证。单文件原生检查仍限时 120 秒，文件数量和容量边界不变。超过预算会失败，不能当作验证通过或自动发布授权。
